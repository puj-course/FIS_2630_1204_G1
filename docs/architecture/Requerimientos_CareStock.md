# Especificación de Requisitos de Software - CareStock

| CÓDIGO   | ESPECIFICACIÓN DE REQUISITOS                                                                                                                                                                   | PRIORIDAD   | ALCANZABLE                                                                                                                | MEDIBLE                                                                                                                                    | TIPO DE REQUISITO (FURPS+)   |
|:---------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:------------|:--------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------|:-----------------------------|
| R01      | El sistema debe permitir al usuario registrar una orden de despacho indicando cliente, producto, cantidad, fecha de despacho y dirección de entrega.                                           | Alta        | Es factible, ya que se trata de un CRUD con campos definidos y validaciones estándar.                                     | Se medirá por la cantidad de órdenes de despacho registradas exitosamente en el sistema, con todos los campos obligatorios completos.      | Funcional                    |
| R02      | El sistema debe generar un número de seguimiento único para cada orden de despacho registrada.                                                                                                 | Alta        | Factible, mediante un algoritmo de numeración correlativa o UUID.                                                         | Se verificará que cada orden tenga un número único, comprobable en la base de datos.                                                       | Funcional                    |
| R03      | El sistema debe permitir actualizar el estado de una orden de despacho a: "Pendiente", "En tránsito", "Entregado" o "Cancelado".                                                               | Alta        | Factible, mediante un campo de estado y una interfaz donde se pueda actualizar.                                           | Se medirá por la cantidad de cambios de estado registrados correctamente y reflejados en el historial de la orden.                         | Funcional                    |
| R04      | El sistema debe mostrar un listado de todas las órdenes de despacho con filtros por fecha, cliente y estado.                                                                                   | Media       | Factible, usando consultas parametrizadas en la base de datos.                                                            | Se verificará que los filtros devuelvan los resultados correctos en menos de 3 segundos para hasta 10,000 registros.                       | Funcional                    |
| R05      | El sistema debe generar un reporte en PDF con el detalle de una orden de despacho específica.                                                                                                  | Media       | Factible, utilizando una librería de generación de PDF.                                                                   | Se medirá por la correcta generación del PDF con todos los datos de la orden y formato definido.                                           | Funcional                    |
| R06      | El sistema debe generar un reporte de despachos por cliente que incluya el total de órdenes y productos despachados en un período de tiempo.                                                   | Media       | Factible, usando consultas SQL agrupadas por cliente y rango de fechas.                                                   | Se medirá verificando que el reporte muestre correctamente los totales de órdenes y productos por cada cliente en el período seleccionado. | Funcional                    |
| R07      | El sistema debe mostrar el número de lote y fecha de vencimiento de los productos en la orden de despacho.                                                                                     | Media       | Factible, ya que estos datos están en el inventario y solo se muestran al momento del despacho.                           | Se medirá verificando que cada orden de despacho muestre correctamente el lote y fecha de vencimiento del producto despachado.             | Funcional                    |
| R08      | El sistema debe registrar en un log de auditoría cada acción realizada sobre las órdenes de despacho (creación, actualización, cancelación).                                                   | Alta        | Factible, mediante triggers o interceptores en la capa de servicio.                                                       | Se medirá verificando que cada acción quede registrada con usuario, fecha, hora y tipo de operación.                                       | Funcional                    |
| R09      | El sistema debe validar que la cantidad de productos despachados no supere el stock disponible por lote en el momento del registro.                                                            | Alta        | Factible, consultando el inventario por lote en tiempo real.                                                              | Se medirá por la cantidad de intentos de despacho con stock insuficiente que sean bloqueados correctamente.                                | Funcional                    |
| R10      | El sistema debe mostrar un mensaje de confirmación antes de finalizar el registro de una orden de despacho.                                                                                    | Baja        | Factible, mediante un cuadro de diálogo en la interfaz de usuario.                                                        | Se medirá verificando que el sistema muestre siempre el mensaje de confirmación antes de guardar la orden.                                 | Funcional                    |
| R11      | El sistema debe aplicar automáticamente el principio FEFO (First Expired, First Out) sugiriendo el lote más próximo a vencer al momento de registrar un despacho.                              | Alta        | Factible, mediante ordenamiento por fecha de vencimiento (`ORDER BY fecha_vencimiento ASC`) en la consulta de stock.      | Se verificará que en el 100% de los despachos el sistema seleccione por defecto el lote con la fecha de caducidad más cercana.             | Funcional                    |
| R12      | El sistema debe permitir la carga e ingreso de nuevos lotes de medicamentos registrando número de lote, cantidad, fecha de vencimiento, registro sanitario INVIMA y ubicación física.          | Alta        | Factible, mediante un formulario de recepción de mercancía con validaciones estricta de campos obligatorios.              | Se medirá por el registro exitoso de nuevos lotes actualizando el inventario general de forma inmediata.                                   | Funcional                    |
| R13      | El sistema debe evaluar diariamente las fechas de vencimiento de todos los lotes y clasificar su estado dentro de un panel semafórico (Rojo: <30 días, Amarillo: 30-60 días, Verde: >60 días). | Alta        | Factible, mediante un procedimiento almacenado / job programado que calcule la diferencia en días contra la fecha actual. | Se verificará que la clasificación semafórica coincida exactamente con los rangos parametrizados para el 100% de los lotes.                | Funcional                    |
| R14      | El sistema debe emitir alertas de stock mínimo cuando la cantidad total disponible de un medicamento sea inferior o igual al umbral parametrizado.                                             | Alta        | Factible, mediante consultas de verificación contra el campo `stock_minimo` de la tabla PRODUCTOS.                        | Se medirá comprobando la generación automática de la alerta en el Dashboard cuando el stock cae por debajo del umbral.                     | Funcional                    |
| R15      | El sistema debe autocompletar la información técnica de los medicamentos (principio activo, concentración, forma farmacéutica) al ingresar el código o nombre en el catálogo base.             | Media       | Factible, realizando búsquedas indexadas en el catálogo maestro prepoblado en la BD.                                      | Se medirá registrando el tiempo de respuesta del autocompletado, el cual no debe superar los 500 ms.                                       | Funcional                    |
| R16      | El sistema debe permitir al Jefe de Farmacia parametrizar y modificar los umbrales de stock mínimo y días de anticipación de alertas por cada producto.                                        | Media       | Factible, mediante una interfaz de configuración restringida por roles con persistencia en la BD.                         | Se verificará que las modificaciones de umbrales actualicen el comportamiento de las alertas de manera inmediata.                          | Funcional                    |
| R17      | El sistema debe permitir la gestión CRUD de proveedores, permitiendo registrar, consultar, editar y deshabilitar información de contacto y productos asociados.                                | Media       | Factible, mediante una vista dedicada y relacional entre las entidades PROVEEDOR y PRODUCTO.                              | Se medirá por la correcta asociación entre proveedores y productos reflejada en las órdenes de compra/reabastecimiento.                    | Funcional                    |
| R18      | El sistema debe generar reportes consolidado de pérdidas por vencimiento (mermas) filtrados por rango de fechas y categorías de medicamentos.                                                  | Media       | Factible, mediante consultas SQL que agrupen los lotes dados de baja por caducidad.                                       | Se verificará que el reporte calcule de forma exacta la cantidad de unidades y el costo total de la merma.                                 | Funcional                    |
| R19      | El sistema debe restringir el acceso a las funcionalidades según el rol del usuario autenticado (Jefe de Farmacia vs. Auxiliar de Farmacia).                                                   | Alta        | Factible, mediante un modelo RBAC (Role-Based Access Control) validado en el backend y frontend.                          | Se verificará que los usuarios con rol Auxiliar no puedan acceder a paneles de configuración ni aprobación de compras.                     | No Funcional                 |
| R20      | El sistema debe permitir la búsqueda en tiempo real de disponibilidad de medicamentos por nombre comercial, principio activo o código de barras.                                               | Alta        | Factible, utilizando índices LIKE / Full-Text Search en Oracle Database.                                                  | Se medirá verificando que la búsqueda devuelva disponibilidad, ubicación y lotes en menos de 1 segundo.                                    | Funcional                    |
| R21      | El sistema debe generar un código de seguimiento único e inalterable (UUID/Correlativo) por cada orden o transacción.                                                                          | Alta        | Factible mediante secuencias numéricas en Oracle DB.                                                                      | Verificación de unicidad comprobable en el 100% de registros.                                                                              | Funcional                    |
| R22      | El sistema debe permitir actualizar el estado de una orden a: Pendiente, En tránsito, Entregado o Cancelado.                                                                                   | Alta        | Factible con actualización de estado en BD e historial de cambios.                                                        | Reflejo del cambio en tiempo real en el historial de la orden.                                                                             | Funcional                    |
| R23      | El sistema debe mostrar un listado de órdenes con filtros acumulativos por fecha, paciente, estado y medicamento.                                                                              | Media       | Factible mediante consultas SQL optimizadas con índices.                                                                  | Tiempo de respuesta de búsqueda menor a 3 segundos.                                                                                        | Funcional                    |
| R24      | El sistema debe integrarse con el módulo de receta médica digital, validando la firma del médico y vigencia de la fórmula.                                                                     | Media       | Factible mediante servicios REST de validación con el RETHUS/IPS.                                                         | Bloqueo automático de despacho si la receta no está firmada o vigencia > 30 días.                                                          | Funcional                    |
| R25      | El sistema debe controlar la entrega parcial de tratamientos crónicos, registrando saldo pendiente y próximas entregas.                                                                        | Alta        | Factible asociando tabla de saldos por formulación y paciente.                                                            | Cálculo exacto del saldo pendiente en dispensaciones fraccionadas.                                                                         | Funcional                    |
| R26      | El sistema debe aplicar automáticamente el principio FEFO (First Expired, First Out) sugiriendo el lote más próximo a vencer.                                                                  | Alta        | Factible mediante ordenamiento ORDER BY fecha_vencimiento ASC.                                                            | 100% de despachos sugieren por defecto el lote con vencimiento más cercano.                                                                | Funcional                    |
| R27      | El sistema debe permitir la recepción y carga de nuevos lotes con registro de INVIMA, lote, caducidad y ubicación.                                                                             | Alta        | Factible con formulario de ingreso y actualización de stock.                                                              | Registro de lotes actualizando el inventario general de forma inmediata.                                                                   | Funcional                    |
| R28      | El sistema debe validar que la cantidad a despachar no supere el stock disponible del lote en tiempo real.                                                                                     | Alta        | Factible consultando stock disponible en BD antes de confirmar.                                                           | 100% de intentos de despacho sin stock bloqueados con mensaje descriptivo.                                                                 | Funcional                    |
| R29      | El sistema debe permitir realizar transferencias y reubicación de lotes entre bodegas o estantes internos con registro de movimiento.                                                          | Media       | Factible creando tabla de transferencias entre ubicaciones lógicas.                                                       | Actualización automática de saldos en bodega de origen y destino.                                                                          | Funcional                    |
| R30      | El sistema debe permitir realizar tomas físicas de inventario (auditoría/conteo) y registrar ajustes por descuadre con justificación.                                                          | Alta        | Factible creando módulo de conciliación de inventario y notas de ajuste.                                                  | Generación de acta de descuadre y actualización auditada del stock físico.                                                                 | Funcional                    |
| R31      | El sistema debe clasificar diariamente el estado de vencimiento en un panel semafórico (Rojo: <30d, Amarillo: 30-60d, Verde: >60d).                                                            | Alta        | Factible mediante procedimiento almacenado y vista dinámica.                                                              | 100% de coincidencia entre dias a vencer y color asignado.                                                                                 | Funcional                    |
| R32      | El sistema debe emitir alertas automáticas cuando el stock total de un producto sea menor o igual al umbral mínimo.                                                                            | Alta        | Factible mediante comprobación automática contra parámetro stock_minimo.                                                  | Notificación inmediata en el Dashboard al caer por debajo del stock mínimo.                                                                | Funcional                    |
| R33      | El sistema debe enviar notificaciones multicanal (Email y SMS/WhatsApp) al Jefe de Farmacia cuando un lote crítico esté a <15 días de vencer.                                                  | Media       | Factible integrando API externa de Twilio o SendGrid.                                                                     | Envío exitoso de la alerta al correo/teléfono registrado del responsable.                                                                  | Funcional                    |
| R34      | El sistema debe permitir el mantenimiento (CRUD) del catálogo de proveedores y asociación a productos.                                                                                         | Media       | Factible con entidades relacionales PROVEEDOR y PRODUCTO.                                                                 | Vinculación correcta de proveedores en compras e inventario.                                                                               | Funcional                    |
| R35      | El sistema debe generar sugerencias automáticas de orden de compra basadas en rotación histórica y stock mínimo.                                                                               | Alta        | Factible calculando consumo promedio diario y punto de reorden.                                                           | Generación de borrador de orden de compra con cantidades calculadas automáticamente.                                                       | Funcional                    |
| R36      | El sistema debe permitir la recepción y cotejo de órdenes de compra contra la factura del proveedor y física de lotes.                                                                         | Media       | Factible creando formulario de recepción con validación de diferencias.                                                   | Registro de discrepancias entre lo pedido y lo efectivamente recibido.                                                                     | Funcional                    |
| R37      | El sistema debe generar reportes en PDF y Excel de mermas/pérdidas por vencimiento calculando valor financiero.                                                                                | Media       | Factible agregando datos de lotes dados de baja por caducidad.                                                            | Cálculo exacto del costo total de pérdidas por lote en el periodo.                                                                         | Funcional                    |
| R38      | El sistema debe generar el reporte normativo obligatorio para Entes Territoriales / INVIMA sobre medicamentos de control especial.                                                             | Alta        | Factible estructurando consultas bajo la norma de la Resolución 1403.                                                     | Generación de archivo plano en el formato estandarizado por el Ministerio de Salud.                                                        | Funcional                    |
| R39      | El sistema debe ofrecer un Dashboard analítico interactivo con proyección de demanda y medicamentos de mayor rotación.                                                                         | Baja        | Factible integrando gráficos con librerías de Chart.js / PowerBI API.                                                     | Visualización de indicadores KPI de inventario en tiempo real.                                                                             | Funcional                    |
| R40      | El sistema debe registrar en un log de auditoría inmutable toda creación, edición o eliminación de datos crítica.                                                                              | Alta        | Factible con triggers en BD e interceptores de eventos.                                                                   | Registro de usuario, IP, fecha, hora y datos previos/nuevos en cada evento.                                                                | No Funcional                 |
| R41      | El sistema debe aplicar control de acceso basado en roles (RBAC) delimitando vistas entre Jefes, Auxiliares y Auditores.                                                                       | Alta        | Factible con middleware de autenticación y autorización.                                                                  | Bloqueo efectivo de vistas administrativas a usuarios sin permisos.                                                                        | No Funcional                 |
| R42      | El sistema debe exigir autenticación multifactor (MFA) mediante código OTP para operaciones de ajuste manual de inventario.                                                                    | Media       | Factible integrando librería TOTP (Google Authenticator).                                                                 | Solicitud del código OTP previa a la ejecución del ajuste de stock.                                                                        | No Funcional                 |
| R43      | El sistema debe registrar y graficar lecturas de temperatura y humedad para medicamentos que requieren cadena de frío.                                                                         | Alta        | Factible mediante ingesta de datos de sensores IoT o registro manual diario.                                              | Alerta sonora/visual al registrar lecturas fuera del rango de 2°C a 8°C.                                                                   | Funcional                    |
| R44      | El sistema debe permitir la consulta de trazabilidad inversa (track & trace) desde un número de lote hacia todos sus receptores.                                                               | Alta        | Factible realizando consulta recursiva en el historial de despachos.                                                      | Listado completo de pacientes y fechas que recibieron unidades del lote en <2s.                                                            | Funcional                    |
